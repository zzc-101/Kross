# 实施方案：知识库 MCP、控制面加固、飞书渠道与文件工作区

依据 [2026-09-01 架构评审](architecture-review-2026-09-01.md) 制定，2026-09-11 修订当前优先级。
每阶段末尾附验收标准，验收由产品负责人执行。

**当前优先级：阶段四（文件上传与管理）。** 阶段一至三代码已落地，产品验收仍由负责人执行。

## 背景与总体顺序

1. 阶段一：把知识库从半成品收口为"MCP 契约下的可选插件"。**代码完成。**
2. 阶段二：控制面加固（测试补齐、事件总线外置、`AgentService` 拆分）。**代码完成**；Helm 默认仍为 `replicaCount: 1`，多副本验收未做，不阻塞阶段四。
3. 阶段三：飞书私聊渠道，防腐层形态。**代码完成**；中间进度摘要未做，不纳入本轮。
4. 阶段四：工作区文件上传与管理。浏览器目前只能列目录和预览 UTF-8 文本，成员无法把资料放进 `/work`，也无法带走产物。这是当前主线。

## 阶段一：知识库 MCP 闭环

**状态（2026-09-01）：代码完成。** 控制面 `/mcp/knowledge`、`knowledge_search`、组织开关、Worker 注入与测试、文档均已落地。鉴权复用 agent token。外部 RAG provider 未做。

### 已核实的现状

- 控制面 `AgentService.workerSettings()` 已按 agent 下发 `mcpServers`（存于 `AgentSettings.mcpServers` JSONB）。
- Worker 宿主收到设置后写入工作区 `.kross/mcp.json`（`worker/src/agentLoop.ts` / `workspaceCommands.ts`）。
- `worker/core/src/mcp/` 具备完整 MCP 客户端：`streamable-http` 与 stdio 传输、按 server 的 `risk` 覆盖
  （默认 `network` 需确认，声明为 `read` 则免确认）、`authorization: bearer-env` 鉴权。
- 知识库服务只有 REST（`/v1/ingest`、`/v1/search`、`/v1/jobs`、`/health`），Worker 侧无任何引用。
- 控制面已有 `KnowledgeClient`（REST 调用封装）与组织级鉴权体系。

结论：缺口只在"MCP server 端点"与"配置注入"两处，客户端链路已就绪。

### 方案选型

推荐方案 A：MCP facade 由控制面（backend）托管。

- 控制面新增 streamable-http MCP 端点（如 `/mcp/knowledge`），最小实现 `initialize`、`tools/list`、`tools/call` 三个 JSON-RPC 方法，暴露唯一工具 `knowledge_search`。
- 鉴权复用现有 Worker agent token（bearer），从 token 解析组织，天然完成租户隔离与 space 范围限定。
- facade 内部经 `KnowledgeClient` 调自建知识库；未来外部 RAG 服务作为另一种 provider 在 facade 后面路由，MCP 契约对 Worker 保持不变。
- 原生支持 MCP 的第三方知识服务可以不经 facade，直接作为受管 MCP server 注入 `mcpServers`。

不推荐方案 B（在 Python 服务内实现 MCP server）的原因：租户隔离与鉴权需要在 Python 侧重建一份；
只覆盖自建知识库，外部 RAG 仍需另做；与"知识库保持可选插件"的定位冲突。

### 改动清单

| 位置 | 改动 |
|---|---|
| `backend` | 新增 MCP facade 控制器（initialize / tools/list / tools/call），`knowledge_search` 工具走 `KnowledgeClient.search`，按组织限定 spaceIds |
| `backend` | 组织开启知识库且服务就绪时，`workerSettings()` 动态合入 `knowledge` server 条目：`transport: streamable-http`、`url` 指向 facade、`risk: "read"`、bearer 用 Worker 已持有的 agent token |
| `admin-web` | 组织级"知识库工具"启用开关（沿用现有知识库管理页面） |
| `worker` | 无需改动；建议补一条集成测试：`mcpServers` 含 streamable-http 条目时 `knowledge_search` 出现在工具列表且 risk 为 read |
| `docs` | `technical-overview.md` 工具边界一节补充受管知识库工具；`configuration.md` 补充开关说明 |

### 验收标准

1. 管理端开启知识库后，成员新会话中 Agent 能通过 `knowledge_search` 检索到该组织已发布文档，且不弹外部确认。
2. 关闭开关或知识库服务不可用时，工具不出现在会话中，会话其余功能不受影响。
3. 组织 A 的会话检索不到组织 B 的文档（用两个组织各建一篇文档验证）。
4. `pnpm test`（worker）、`./mvnw test`（backend）通过。

## 阶段二：控制面加固

**状态（2026-09-01）：代码完成。** 租约 / 事件摄入 / 隔离测试已补；`ChannelEventBus` 经 Redis Pub/Sub 扇出，故障降级进程内；`AgentService` 已拆为会话、Worker 协议、租约、记忆四个服务。`deploy/cluster/values.yaml` 默认仍为 `replicaCount: 1`，多副本与滚动发布验收未做，不作为阶段四前置。

### 2.1 核心路径测试补齐（先于拆分）

优先覆盖三条路径，均针对现有 `AgentService` 行为建立回归基线：

- 租约：`claimJob` 并发认领唯一性、`recoverExpiredJobLeases` 过期回收、`releaseClaimedJob` 幂等；
- 事件摄入：`ingestEvents` 乱序与重复投递的幂等性、`postReply` 最终快照落库；
- 隔离：跨组织访问会话 / 记忆 / 工作区均被 `OrganizationAccess` 拒绝。

### 2.2 事件总线外置

- 将 `ChannelEventBus` 的进程内扇出替换为 Redis Pub/Sub（Redis 已在技术栈内，沿用"纯缓存、可丢失"定位：SSE 断连由前端重连 + 最终快照兜底，不要求消息持久化）。
- 保留进程内路径作为 Redis 不可用时的降级（单副本场景行为不变）。
- 完成后解除 `deploy/cluster/values.yaml` 的 `replicaCount: 1` 限制并更新注释。

### 2.3 `AgentService` 拆分

以 2.1 的测试为安全网，按职责拆为三个服务，Mapper 与事务边界不变：

- 会话与记忆（conversation / message / memory / workspace 读取）；
- Worker 协议（register / heartbeat / claimJob / postReply / ingestEvents / workerSettings）；
- 租约与调度（唤醒、休眠、租约恢复、清理任务）。

### 验收标准

1. 新增测试全部通过，且能演示一次"故意破坏租约逻辑导致测试失败"。
2. 集群模式 `replicaCount: 2` 下：两个浏览器会话分别路由到不同副本时，流式输出均正常；滚动发布期间进行中的会话在重连后能看到最终结果。
3. 拆分后 `AgentController` 等调用方仅改依赖注入，REST 与 WebSocket 协议无变化（前端与 Worker 零改动）。

## 阶段三：飞书渠道接入（设计级，启动前需细化）

**状态（2026-09-02）：私聊 MVP 代码完成。** 独立 `connector` 模块、绑定码、inbox 先持久化再处理、完成/失败回工作台链接、外部工具飞书卡片确认均已落地。未做关键进度摘要；群聊与企业微信不在范围。

### 原则

- 防腐层：新增独立 channel adapter 模块，把飞书 webhook 归一化为现有会话 API 调用；核心会话模型保持渠道无关，"飞书"概念不进入 `AgentService` 及其拆分后的服务。
- 飞书先行：组织导向与多租户 / 企业 SSO 定位对齐；企业通讯录可映射成员身份；消息卡片可承载外部工具确认。个人微信无官方机器人 API，不做；企业微信作为后续候选。

### 关键设计点

| 问题 | 方向 |
|---|---|
| 身份映射 | 飞书 open_id / union_id 与 Kross 成员的绑定表，首次使用时通过绑定流程确认 |
| 回调可靠性 | webhook 入口先持久化再异步处理（依赖 2.2 完成）；按飞书事件 id 去重 |
| 长任务形态 | 不映射流式输出；采用"收到任务确认 → 关键进度摘要 → 完成后产物链接（回工作台查看）"的异步模式 |
| 工具确认 | 外部工具确认以飞书消息卡片按钮承载，复用现有 approval 协议 |

### 验收标准（启动前随细化方案修订）

1. 飞书私聊机器人发起任务，可在工作台看到同一会话及产物。
2. 未绑定的飞书用户收到绑定引导而不是执行任务。
3. 涉及外部系统的工具调用在飞书内以卡片确认后才执行。

## 阶段四：工作区文件上传与管理

**状态（2026-09-11）：当前主线，尚未开工。**

### 已核实的现状

- 浏览器只有 `GET /api/v2/agent/workspace/files` 与 `GET /api/v2/agent/workspace/file`：列目录、预览 UTF-8 文本（Worker 侧 `workspace.read` 上限 256KB）。
- Worker `workspace.write` 只接受 UTF-8 字符串、上限 512KB，且仅供记忆 / MCP 配置内部写入，未对浏览器开放。
- 文件面板（`FilesPanel`）可浏览与文本预览，无上传、下载、删除、建目录。
- 对话输入框无附件；`MessageParts` 已能渲染 file / image part，但没有写入路径。
- 飞书非文字消息会回复"请发送文字，或到工作台上传附件"，但工作台目前做不到。
- 快速上手写"放入 `/work/files` 的资料"，成员没有对应操作入口。
- 文件事实源是成员 Worker 的 `/work`。控制面不持有文件字节；集群下工作区 RPC 必须打到持有该 Worker WebSocket 的副本。

结论：缺口在"浏览器 ↔ 控制面的二进制协议"和"文件面板 / 对话的管理操作"。Agent 侧 Read / Write / Glob 已能处理工作区文件，上传成功后无需改 Runtime 工具面。

### 方案选型

推荐：继续以 `/work` 为唯一事实源。浏览器走控制面 HTTP，控制面经现有 `agent.command` 把字节写入 / 读出 Worker。

- 不把附件 blob 写入 PostgreSQL，不另建对象存储作为第二文件库。对话消息只引用工作区路径。
- 现有 `workspace.write` 的 UTF-8 JSON 帧撑不住 PDF / 表格 / 图片。新增分片命令（如 `workspace.put` / `workspace.get`），单帧仍遵守现有 WebSocket 文本上限，Worker 按 offset 组装。
- 单文件上限与知识库二进制对齐，建议 10MB；超限在控制面拒绝，不打到 Worker。
- 上传落点：文件面板写入当前目录；对话附件写入约定目录（默认 `uploads/`，重名追加后缀），并在用户消息中带上路径，供 Agent 用文件工具读取。
- 预览：UTF-8 文本维持现状；常见图片（png / jpeg / gif / webp）可在面板内联；其余类型只提供下载，不做 Office 在线预览。

不推荐：控制面先收进 MinIO 再让 Worker 拉取。多一个事实源，失败时"控制面有、工作区没有"，排障和权限模型都更重。

### 改动清单

| 位置 | 改动 |
|---|---|
| `worker` | 新增 `workspace.put` / `workspace.get` / `workspace.delete` / `workspace.mkdir`（及可选 `workspace.move`）；`put`/`get` 分片二进制；路径继续走 canonical realpath，禁止逃逸 |
| `backend` | 成员 API：multipart 上传、二进制下载（`Content-Disposition`）、删除、建目录；鉴权复用 `OrganizationAccess`；超限与类型校验在控制面完成 |
| `frontend/web` | 文件面板：上传（含拖放）、下载、删除确认、新建文件夹；文本 / 图片预览，其他类型引导下载 |
| `frontend/web` | 对话输入框可附加文件：先上传到工作区，再把路径写入用户消息 |
| `docs` | `cloud-protocol.md` 补文件 API；`technical-overview.md` / `security.md` / `getting-started.md` 去掉"附件上传未完成"，写明大小与预览边界 |

### 验收标准

1. 成员可在"文件与产物"把本地文件上传到当前目录，刷新后可见；Agent 新回合能 Read 到该文件。
2. 对话中附加文件后，消息带工作区路径，同一文件出现在文件面板；Agent 能按该路径处理。
3. 产物可从文件面板下载，内容与 `/work` 中一致；超过预览上限的文本与非图片二进制不在面板里当文本打开，只提供下载。
4. 删除文件或空目录后列表立即更新；路径穿越（`..`、symlink 逃出 `/work`）被拒绝。
5. 未唤醒的 Worker 在上传 / 下载时被控制面拉起；Worker 不在线时返回明确错误，而不是把字节丢在控制面。
6. 跨组织不能列举、读取、上传或删除另一组织成员的工作区文件。

## 非目标

- 个人微信接入。
- 知识库 ingest / publish 暴露为 Agent 工具（仍由管理端 REST 承担）。
- MCP facade 支持交互式 OAuth 外部工具（沿用现有边界声明）。
- **对外 MCP 出口**（让 Codex / Claude Code / Cursor 把任务投到本平台 Worker）。不做。
- **降低试用门槛的 all-in-one 镜像、公开演示环境。** 不做。入口维持 `./scripts/start-cloud.sh`。
- 本阶段不做：Office / PDF 在线预览、公开分享链接、文件版本历史、回收站、飞书消息里传文件、把工作区文件当第二套知识库 ingest。
