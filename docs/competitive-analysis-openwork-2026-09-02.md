# 竞品分析：OpenWork 与 Kross

日期：2026-09-02。资料来源为 `different-ai/openwork` 仓库 README、openworklabs.com 官网与 `llms.txt`，以及本仓库 README 与技术概览。
本文用于产品定位与后续优化决策，不是排期文档。

## 一句话定位

| | OpenWork | Kross |
|---|---|---|
| 官方定位 | 开源版 Claude Cowork，套在 OpenCode 之上的桌面 GUI | 组织可自托管的云端电脑 Agent |
| Agent 执行位置 | 用户本机（桌面模式），托管 Cloud workers 为可选 alpha | 组织自己的 Docker / k3s 集群，每人一个远程 Worker |
| 产品形态 | Electron 桌面 App 为主，Web 为 alpha，另有 MCP 网关接入第三方 Agent | 纯 Web，无桌面端、无 CLI |
| Agent 引擎 | 复用 OpenCode | 自研 Runtime（`worker/core`） |
| 组织控制面 | OpenWork Den，EE 授权，商用收费，以 SaaS 为主 | 控制面属于 MIT 主体，多组织 / 角色 / OIDC 开箱即有 |
| 商业模式 | 开源核心 + EE 收费 + 托管订阅（5 人以下免费，之后 10 美元/人/月） | 全 MIT |
| 背景 | YC 背书，2026-01 立项，约 2.3 万 star | 预发布阶段 |

两者的核心分歧只有一条：**OpenWork 的 Agent 跑在员工的电脑上，Kross 的 Agent 跑在组织的服务器上。** 下文的大部分优缺点都是这条分歧的推论。

## OpenWork 的优势

1. **生态位开放。** OpenWork MCP 网关把组织分配的 Skill、MCP 连接、Google Workspace / M365 能力打包成一个远程 MCP 地址，可以直接塞进 Codex、Claude Code、Cursor。它不与现有 Agent 客户端争夺入口，而是给它们供能力，企业已有的工具链可以直接接入。
2. **模型覆盖面借力 OpenCode。** 50 余家 provider、本地模型开箱可用，模型适配成本由上游承担。
3. **Skill / 插件生态启动快。** 已有插件市场、Anthropic 兼容插件导入、定时任务与浏览器自动化插件。
4. **本地执行的合规叙事。** "文件不出本机，prompt 直连模型厂商"对个人用户与小团队是直观可信的隐私承诺。
5. **零部署门槛。** 下载即用，Solo 免费 BYOK，5 人以下团队免费，获客漏斗顺畅。
6. **社区与资本。** 高 star 数带来贡献者、Issue 反馈与 SEO；YC 背书带来企业销售的可信度。

## OpenWork 的劣势

1. **执行体是员工的笔记本。** 算力、在线时长、数据落盘位置都归个人。合上电脑任务就停，定时任务依赖本机开机，长任务（数小时的整理与生成）没有可靠宿主。
2. **组织治理是"下发策略到端"，不是"在服务端持有执行"。** Den 可以控制客户端版本、限制本地模型访问，但执行仍在端上，管理员对运行态的可观测与可干预能力受限。
3. **私有化不是默认形态。** Den 是 EE 收费件且以 SaaS 为主，私有部署需走企业采购谈判；有数据不出内网要求的组织进不了免费漏斗。
4. **服务端能力薄。** 开源部分的服务端只是单机 `openwork-server`，没有多副本、共享工作区、Worker 调度这一层。Cloud workers 仍在 alpha。
5. **能力边界随 OpenCode 走。** 作为 OpenCode 的 GUI，其 Agent 行为、工具边界、上下文策略受上游约束，深度定制空间有限，且上游是编程 Agent 基因，知识工作场景的行为约束需自行补足。
6. **桌面 App 的企业分发成本。** 异构设备、版本管理、终端安全策略都会成为企业 IT 的阻力，这也是他们把桌面端降级为"可选"的原因。

## Kross 的优势

1. **"云端电脑"架构。** 每位成员独立 Worker 与持久 `/work`，任务在服务端常驻，员工设备只是浏览器。对合规（数据不落员工本地）、长任务、设备异构三类企业场景，这是 OpenWork 架构上补不了的短板。
2. **私有化是默认形态。** 控制面、多组织、角色、OIDC、模型与 Skill 的平台管理都在开源主体里，`helm install` 即有，不需要"企业版"这一层。
3. **成员不接触密钥。** 模型密钥与 SSO 密钥加密存放于控制面，成员不填 API Key、不选运行模式、不配权限档位，管理面收敛。
4. **服务端多节点的工程基础。** 控制面多副本、Redis 缓存与跨副本 Pub/Sub 扇出、Worker 租约、JuiceFS 共享工作区、k3s Helm 部署，这是 OpenWork 当前没有的一层。
5. **收敛的工具边界与确认模型。** Runtime 只注册文件 / 检索 / Todo / Task，不注册 Shell、Git；工作区读写自动，外部副作用必须确认，checkpoint 恢复时不重放已完成副作用。这对面向非程序员的知识工作是更安全的默认值。
6. **结果结构化。** `artifacts` / `evidence` / `incompleteItems` 三元组让结果可审计、可交接，而不是一段聊天文本。

## Kross 的劣势

1. **封闭 Runtime，没有接入路径。** 企业若已在使用 Codex / Claude Code / Cursor 等客户端，Kross 无法向它们供能力，也无法被它们调用。OpenWork 的 MCP 网关策略正好填在这个位置。
2. **没有 Skill 市场与外部插件导入。** Skill 是平台内部版本化分发，缺少生态启动机制；Anthropic 兼容插件、社区 MCP 的接入需管理员逐个配置。
3. **部署门槛高于"下载即用"。** 需要 Docker 或 k3s、PostgreSQL、对象存储，个人用户与小团队难以形成免费试用漏斗，缺少低门槛的获客入口。
4. **模型接入靠自研。** provider 适配、能力探测、可观测都需自行维护（见 `provider-capabilities.md`、`provider-observability.md`），覆盖面短期内追不上 OpenCode 的上游。
5. **文件交互仍有缺口。** 浏览器附件上传尚需独立协议，文件面板只有目录浏览与文本预览；受管外部工具不支持所有交互式 OAuth。
6. **工程成熟度与社区。** 预发布阶段，生产环境在 TLS、弱网、移动端、备份恢复场景尚未验收；没有外部贡献者与用户反馈回路。
7. **名称近似冲突。** `KrossWork` 与桌面 AI Agent 产品 `KroWork`（krowork.com）同品类、差一个字母，长期存在搜索与口头传播混淆风险。

## 建议

以下按优先级排列，前三项直接关系到定位是否成立。

### 1. 把"企业私有化云端 Agent 集群"这个位置先占稳

OpenWork 已在做 OpenWork Web 与 Cloud workers，说明他们也在往服务端执行走。等其成熟，两者定位差距会缩小。Kross 的窗口期在于服务端这一层的成熟度：多副本控制面的一致性、Worker 调度与回收、JuiceFS 工作区在真实集群下的稳定性、备份恢复。
对外叙事应压在三点：任务常驻、数据不落员工设备、开源即私有化。避免使用"Cowork 替代品"这类会与 OpenWork 撞车的话术。

### 2. 补一条对外接入路径

**2026-09-11 决定：不做。** 不提供把任务投递给 Codex / Claude Code / Cursor 的 MCP 出口。飞书渠道已按私聊 MVP 落地，不再为此预留共用协议层。

### 3. 降低试用门槛

**2026-09-11 决定：不做。** 不提供 all-in-one 镜像或公开演示环境。入口维持 `./scripts/start-cloud.sh`。

### 4. Skill 与 MCP 的生态接入

- 支持导入 Anthropic 兼容插件格式与社区 MCP server 定义，减少管理员逐个手工配置的成本。
- 考虑一个组织内的 Skill 目录（不必是公开市场），让组织管理员可以从平台提供的基线 Skill 包中挑选启用，而不是只能上传。

### 5. 强化管理员对运行态的可观测与干预

这是服务端执行相对端上执行的结构性优势，应把它做成显性卖点。`product-backlog.md` 中的"Agent 运行观测中心"方向正确，建议提高优先级：按组织 / 成员查看运行中任务、工具调用、确认等待、资源占用，并支持管理员终止任务。OpenWork 的 Den 做不到这一层。

### 6. 补齐文件交互

**2026-09-11：当前主线，见 `roadmap-2026-09-01.md` 阶段四。** 浏览器附件上传、文件面板管理（上传 / 下载 / 删除）和产物取回优先；公开分享链接与 Office 在线预览不纳入本阶段。

### 7. 技术标识中性化

不论产品名是否变化，配置前缀、环境变量、Cookie、localStorage、k8s 资源名等技术标识应与产品名解耦，避免下次品牌调整再做一轮全仓库替换与部署迁移。具体分层与命名映射见 `rename-to-openwork-2026-09-01.md`。

### 8. 名称

本轮决定维持 `KrossWork`。`KroWork` 的近似冲突仍然存在，建议在第一次对外正式发布前重新评估；若届时更名，因技术标识已中性化，成本将只剩文案与仓库名。
